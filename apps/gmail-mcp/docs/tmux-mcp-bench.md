# tmux MCP — benchmark

Generated by [`scripts/bench-tmux-mcp.ts`](../scripts/bench-tmux-mcp.ts). See [`docs/tmux-mcp-setup.md`](./tmux-mcp-setup.md) for the wiring recipe both servers depend on.

## TL;DR

- **`tmux-mcp-rs` wins decisively on cold start (~59×), resident memory (~16×), and tool surface (~4×).** The Rust binary boots in ~15 ms vs the Node binary's ~890 ms (most of which is `npx` resolving the package); RSS holds at ~11 MB vs ~183 MB; the Rust server exposes 55 tools (full tmux surface including `send-keys`, buffer ops, layouts) vs 13 from the Node server.
- **Per-call latency is much closer.** On a hot connection both round-trip a tmux op in single-digit ms; the Node server is slightly faster on the `execute-command` write path (7.7 vs 10 ms p50) and on the 10-parallel fan-out (20 vs 34 ms wallclock), while Rust edges out on the idle `list-sessions` path (5.1 vs 7.1 ms p50).
- **Recommendation: `tmux-mcp-rs`** for general use. Cold-start and memory dominate the experience when the MCP is wired into an agent host that respawns it per conversation. The Node server's narrower tool surface is also limiting — no `send-keys`, no buffer ops, no pane layout control.

## Methodology

- **Cold start**: time from `StdioClientTransport.start()` to first `tools/list` response. The very first run is discarded as warmup (npx in particular pays a one-shot dependency-resolution cost); the reported value is the second run.
- **Round-trip idle**: 50 sequential `list-sessions` calls against a hot connection.
- **Round-trip write**: 30 sequential `execute-command` calls running `true` inside a dedicated `bench-*` session.
- **Throughput**: 10 parallel `execute-command` calls via `Promise.allSettled`; reports total wallclock + rejected count.
- **Memory**: 6 samples of `ps -o rss=` against the server's own pid, 1000ms apart.
- **Tool surface**: `tools/list` length. Both servers expose overlapping verbs; the Node implementation has a smaller surface (no `send-keys` variants, no `buffer-*`, no `layout/zoom` controls).
